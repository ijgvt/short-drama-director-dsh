# H3 出视频（一采 + 二采，直出二采）

> **使用的工作流：`YZ金鱼-MiniMax H3 终极篇-文武双全`**
> 逐节点核实的完整说明见 `references/工作流-终极篇-文武双全.md`——**改参数前先读它**。
>
> **旧的《YZ金鱼-MiniMax+H3-多参考生视频-优化版》已停用。** 那条工作流的两模式（一采抽卡 / 二采）
> 与本文档描述的流程**不再一致**，不要再用它的节点号或参数。


> **格式与转换规则以 `skills/h3-prompt-converter/SKILL.md` 与其 `references/source-format.md` 为准**，后者再引用上游官方规范：
> 就是本插件自带的 `h3-prompt-writing` 技能里的 `references/base-en.txt`（T2VA 等三字段）与
> `ref-en.txt`（Ref2VA 六段式）。**写提示词前先读这两份，不要凭理解写。**
> 这两份在**插件包里**，不要去 `~/.codex/` 找——那个目录只在装过那个工具的电脑上才有。
>
> `references/source-format.md` 里有一张**逐字段映射表**，【摄像机景别】【拍摄主体】【画面】的每个子项该落到哪里都写在里面。最容易漏的几条：
>
> | 源字段 | 落到 H3 的哪里 |
> |---|---|
> | 【摄像机景别】景别词 | 只用官方词表：中文 `中景` / `近景` / `中远景` / `大特写`，英文 `a medium shot` / `a close shot` / `a medium-wide shot` / `an extreme close-up`（源里的 `特写` → `大特写` / `an extreme close-up`） |
> | 【摄像机景别】固定机位 | `固定机位` / `static shot`，或干脆不写运镜分句 |
> | 【摄像机景别】运镜 | motion type + amplitude + speed，如 `缓慢小幅推近` / `pushes in with small amplitude at slow speed` |
> | 【拍摄主体】 | **无官方字段**——在该镜开头写 `镜头对准 X`（英文 `framing X`）。人物**面部特写**追加 `45° 侧面特写`；非面部特写不加 |
> | 【画面】动作走位 / 微表情神态 / 视线方向 | 同一句里的 action / expression / gaze 三个分句，按此顺序 |
> | 台词 `开口说：“…”` | `<d>[Chinese] …</d>`，说话人带 `(Sx)` |
> | 【初始站位】轴线声明 | 一句话写进描述，如 `全片机位保持在 X 的右侧，始终不越轴。`——**只在源里声明了轴线时才写** |
> | 【画面风格和类型】 | `实拍电影风格` / `Live-action, cinematic` 作为开头风格句 |
>
> 切镜写法嵌在句子里，照样例：`在 00:01.500 切至 <Subject 1> 的近景` / `At 00:01.500, the shot cuts to a close shot of <Subject 1>`。
> 另外三条通用要求：
>
> | 项 | 要求 |
> |---|---|
> | `subject_definitions` | **只做通用绑定**：给出标签、名称、以及"哪些方面跟随参考图"。**绝不罗列参考图里可见的物件、颜色、材质**——图自己带着这些，写错等于和图打架 |
> | 文风样板 | 丢掉 `8K超高清`、`禁止过度锐化` 这类分辨率与反伪影套话。只留具体的摄影事实（镜头、灯光、景深、胶片感），一两句，写在 `[Shot 1]` **之前** |
> | `non_diegetic_music` | 默认 **`N/A`**（见下方硬规则 3） |

工作流：**`YZ金鱼-MiniMax H3 终极篇-文武双全`**。H3 单次只能出 **4–15 秒**，所以**一个大分镜跑一次**，分镜在 prompt 里写成 `[Shot N]`。

**只有一种流程：一采 + 二采，直出二采。没有一采抽卡。** 一采在低分辨率上试、二采放大后精修，**最后的产物就是二采的结果**——一次提交就是成片。

## 文件按大分镜分块（一个 H3 文件只放一个大分镜）

**code 与面板的当前契约是：每个大分镜一份独立 H3 文件**，文件名形如
`第1集H3提示词-大分镜1（中文）.txt`。每份文件都是一条完整、可独立粘贴的 H3
提示词，`subject_definitions` 必须自包含。

一份文件里不再用 `---` 拼接多个 H3 块。`compile-h3`、`sync-h3` 和
`generate-h3` 都按“一个文件 = 一个大分镜”工作；提交时传该文件并固定
`index=0`。旧的多块文件仍能读取，但不能作为新生成的目标格式。

**两条硬规则：**

1. **每个块都要重写 `subject_definitions`。** 不能靠"见上一个块"——块是拿来单独粘贴的。
   `<Picture N>` 的编号**按本块 `subject_definitions` 的书写顺序**算，所以上传参考图时也按块来。
2. **文件内的 `subject_definitions` 只写本大分镜实际出场的角色/场景/道具。**

**素材栏和提示词正文是两套状态。** 用户点“一键同步”时，**最新视频提示词是参考槽的唯一真相**：当前会话模型只读取文字并生成 H3 正文字段，不读图；代码按视频提示词里写的用途重建 `<Subject>/<Picture>/<Audio>/<Video>`。正常转换是一次模型调用，并且**不设置人工的小 maxTokens**，使用模型适配器默认预算；只有真的撞到 max-tokens 时，才压缩提示、重试并拆成更小字段批次，不能把整次同步判死。图片功能必须按用户原话解释，例如 `初始站位参考@文件` 写成“初始站位图”，不能把上传文件名当作资产名，也不能因为旧 H3 曾经绑定过就继续保留重复槽。与最新视频提示词不一致的旧槽会被移除并报告。Agent 直接调 Host 时，`sync-h3` 返回的 `text`、`referenceSlots` 和 `discardedReferenceSlots` 要一起核对，再调用 `references` 绑定资产。

`sync-h3` 的入口可以是标准中文 H3 文件，也可以直接是本集视频提示词。前者可从文件名
`大分镜N` 推出块号；后者需要 `blockNumber`。不要把“H3 正文不能含 `@`”理解成同步失败：
`@` 只存在于视频提示词，同步时必须把它编译成 `<Picture N>`，不能反向要求 H3 再写 `@`。
同一路径、同一 sha256 的重复资产索引记录只算一个候选；真正的不同版本仍要求用户选择。

右侧栏「分镜管理」按大分镜文件显示卡片。一个 H3 文件就是一张卡片；需要新增镜头时应新建对应的大分镜 H3 文件，不要把多个大分镜重新塞回同一文件。旧的单文件多块项目仍可查看和编辑，但新模板、编译和提交都使用一文件一块。

## H3 提示词只有中文一份

分镜工作台和导演流程**只生成、修改、上传中文 H3**。不再生成英文伴生稿，也不再提供英文翻译或英文同步。

**硬规则：**

1. **推荐字段名使用英文，正文使用中文。** 下面是推荐结构，不是提交前置条件；缺字段、少字段或顺序不同也可以直接生成：
   `subject_definitions` / `summary` / `retention_analysis` / `detailed_description` /
   `overall_soundscape` / `non_diegetic_music`。不要改字段名，不要合并或重排。
2. **中文稿就是最终喂给 ComfyUI 的稿子。** 编译、编辑、上传、生成都使用同一份中文 H3，不再另存或寻找英文版。
3. **台词、唱词、画面可见文字保持中文原文**，写在 `<d>[Chinese] 台词原文</d> (S1)` 里。
4. **`non_diegetic_music` 默认写 `N/A`——不要 BGM。** 短剧的配乐是后期统一做的，提示词里自带一段音乐等于和后期打架，而且 H3 生成出来的音乐**去不掉**。音效、环境音、对白该写就写（写在 `overall_soundscape` 与 `detailed_description` 里），**只有"观众才能听到的配乐"这一项留空**。

`retention_analysis` 中一个主体如果只在站位/映射里出现、没有任何镜次，写成
`<Subject N> (not visible in any shot): weak_reference - 仅作为站位或上下文参考，不得画入任何镜头。`
不要省略括号，也不要把它写成 `fully_preserved`；上游 validator 要求每行都有括号说明。

   ```
   overall_soundscape:
   全片持续着雨夜书店的安静底噪：窗外连绵的雨声与檐口滴水，旧书页摩擦的干脆响声。（音效照写）

   non_diegetic_music:
   N/A
   ```

   **只有用户明确要求某一段要有配乐时才写内容**，并注明是他要求的。字段本身**不能省**——省掉是格式错误。

用技能自带的校验器验中文文件：

```
python skills/h3-prompt-converter/scripts/validate_h3_prompt.py "<中文提示词文件>"
```

### 插件按实际图片数动态接线

上表是原始工作流状态，不是本插件的固定容量。面板生成时，`prepareH3Graph` 会按提示词里的
`<Picture 1..N>` 建立同样数量的加载节点和参考输入，只接入本次真正需要的图片：

- 1–9 张参考图都由插件自动接线，不需要用户先去 ComfyUI 取消旁路或手工选图。
- 未使用的旧 LoadImage 会被旁路，避免请求上一部戏的残留文件。
- 只有超过 **9 张**时才要求用户合并角色/场景参考或在资产页删减；必须明确告诉用户超了几张，不能静默把道具降级成文字。
- 参考音频/视频是否可用取决于当前工作流适配器；图片工作流不能假装接收音频/视频。

### 出视频前必须做的事

1. **按提示词里 `<Picture N>` 的顺序准备参考图**。面板会按同一顺序动态上传；不要再把节点号
   `#51/#49/#50` 写死到用户指令里，节点号随工作流保存会变化。
2. **`ref_image_size`**：`match`（默认，按生成分辨率缩放，快）/ `max`（2048px 短边，身份保真最好但**慢好几倍**）。当前工作流是 `max`。
3. **音频**：`ref_audios` 是**参考音频**（音色/节奏条件），不是成片音轨；成片音轨由 `#254 VAEDecodeAudio` + `#364 VHS_VideoCombine` 生成。

### 人物音色自动引用

- 视频提示词和 H3 里出现的每个角色，只要该人物资产上传过 `role: voice` 音色，就要自动进入当前块的音频素材槽；没有音色的角色跳过，整条旧流程不变。
- 一个块最多自动带入**前 3 位有音色的人物**，顺序按角色在该块中第一次出现的顺序。第 4 位及以后不再添加。
- 用户显式绑定的音频优先，先占音频槽；自动音色只填剩余的空槽，不会覆盖或重复人物已有音色。
- 自动音色是面板管理的素材绑定，**不改写用户 H3 提示词正文**。生成时仍把当前 H3 原文逐字提交；即使正文没有新写 `<Audio N>` 定义，自动槽也属于已绑定的可用输入。
- 短剧导演不得合成、克隆或判断音色好坏；用户删除音色后，下一次解析只移除该自动槽，不影响其他显式音频与其余素材。

### 素材数量是硬的

| 约束 | 值 |
|---|---|
| 所有素材（图 + 视频 + 音频）**混合总数** | **≤ 12** |
| 参考图像 | **≤ 9** |
| 参考视频 | ≤ 3 段，每段 2–15 秒，总时长 ≤ 15 秒 |
| 参考音频 | ≤ 3 段，需与图像或视频搭配，总时长 ≤ 15 秒 |

## 出视频前的资产准备：每集穿什么衣服

视频提示词里人物是按 **`@角色名（造型）`** 引用的，所以**每一集的每个角色用到哪几套衣服，必须先定下来再出视频**，否则参考图会对不上、模型会自己换衣服。规划方式：

- 盘点稿的「形态变体表」已经列了每个角色的全部造型；**每一集要用哪一套**在写本集剧本前 3 段时就定死，并写进该集 `dataset.json` 的 `characters` 数组（写变体全名，如 `男主（军装造型）`）。
- 一个角色在一集里有多套衣服 → **每套都要有独立的 9:16 定妆照 + 16:9 四视图**（走 `costume-and-quadview` 的换装流程），不要指望一套图改提示词顶两套。
- 出这一集视频时，把这一集实际出场的那几个造型的四视图按提示词里的 `<Picture N>` 顺序上传。
- 同一场景多集复用 → 场景图只做一次，但每集都要 `drama_workspace` `action=sync_asset` 同步进去。

## 出视频前先过一遍校验

`comfy_run` 会在提交后立刻返回 ComfyUI 的 `node_errors`，**先看这个再等**，能省掉一次白跑。

这条工作流特有的三类问题：

1. **插件生成的图不应仍引用旁路 LoadImage** —— `prepareH3Graph` 会旁路未使用的 LoadImage；
   如果手工调用 `comfy_run`，先用 `comfy_graph` 核对实际输入，不要把旧的旁路节点当成已接线。
2. **旁路的参考视频 `VHS_LoadVideo#27/#25/#26` 没选文件** —— 用不到就保持旁路。
3. **`MiniMaxChunkFeedForward` 爆显存** —— 作者的处置办法（原话）：
   > 如果还爆显存就把 Chunks 调成 4 或者 8，seq 调成 2048

**云端是 RTX 4090（23.5 GB），本地是 RTX 3060 Laptop（6 GB）**——同一套参数在本地大概率爆显存，
本地跑必须先按第 3 条降配。这一步只调节点值，**不要动 `GetNode/SetNode` 的名字**（见下）。

### 改这份工作流的一条铁律

**不要改 `GetNode` / `SetNode` 的名字。** 这份工作流用 **46 个虚拟连线节点**（24 GetNode + 22 SetNode）
按**名字**配对，不靠连线。改错一个名字会让整条参考链**静默失效**——不报错，只是参考图不生效。

### 两个步数的关系

`基础调度器.steps`（总）与 `transition_step`（一采）共同决定切分，**两种模式各有一套值**：

| 模式 | 总步数 `steps` | 一采 `transition_step` | 二采（差值） |
|---|---|---|---|
| **文戏** | 12 | 8 | 4 |
| **武打** | 14 | 10 | 4 |

两者差 4 步是刻意的：武打多出来的 2 步花在一采上（动作镜头需要），二采的细化步数保持一致。
调这两个数字时保持 `transition_step < steps`，否则二采没有步数可分。
**这两项由插件按模式自动写入，不需要手改**——`generate-h3` 会按 `settings.mode` 选表。
只有手工跑工作流时才需要自己填。

### 用哪一份提示词去生成

**面板和 agent 都只使用中文 H3。** 面板把当前中文块的正文原样传给 `generate-h3`；agent 自动生成时也读取同一份中文 H3，不寻找英文文件，不做语言转换。

中文 H3 推荐使用英文字段名和中文正文，但字段不是必需项。它就是最终上传给 ComfyUI 的提示词；不要为了补齐格式而阻断提交。

### agent 调 `generate-h3` 的最小参数

- **一律用 0 起的 `index` 定位块**。`shotId` 不是不能用，它是**单份文件内**的身份：把视频提示词那份、或另一集的 `shotId` 传进来，Host 只会答"这个文件里没有 shotId=X"，白跑一轮。
- `expectedText` 是**可选**的防陈旧参数，不再要求再抄一份正文。Host 会先读取当前磁盘上的 H3 块；如果调用方刚调用过 `storyboard action=read file=<H3文件>`，可以把回执中的 `shot.text`（不含【大分镜N】标题行）原样传入，以拒绝读取后的外部改动。不要手打。
- 时长优先用 `settings.seconds`；不传时 Host 会从对应的视频提示词块继承标题或正文小分镜之和。
- 缺 `index` 会报定位错误；提供了 `expectedText` 且块已变化才会拒绝生成。不提供 `expectedText` 不会阻断生成。

**回执只有一行 / 看不到 `prompt_id` 时：不要重提。** 提交成功但回执很薄是正常现象（实例收下了图，回复里没带 id）。正确动作是 `storyboard action=jobs` 按 `requestId` 反查，看见 `queued`/`running` 就是已经在跑。重提会让同一个镜头在 GPU 上跑两遍，还多出一条分不清的候选。

**参考资产必须能唯一定位到一张图。** 报"有未绑定的 H3 参考资产"时，先看是不是**同名多形态**（`问雪剑` 和它的纸化形态）：一个道具要两种形态就**用两个独立资产名**，不要靠变体猜；`@名字` 一定要落到一张确定的文件上。

### 分辨率怎么选

`megapixels` 决定总像素，`aspect_ratio` 决定比例，`multiple=32` 决定对齐。作者附的对照表（16:9）：

| megapixels | 输出 |
|---|---|
| 0.5 | 960 × 544 |
| 0.98 | 1344 × 768（等于旧工作流的写死值） |
| **1.5** | **1664 × 928**（当前值） |
| 2.0 | 1920 × 1088 |

**竖屏短剧要换成 9:16**，不要照抄当前的 16:9。完整表在 `references/工作流-终极篇-文武双全.md`。

## 出片按大分镜 1→N 顺序，一次一块

- **先大分镜 1，拿到结果再动大分镜 2**。不要并行提交好几块，也不要跳着来。
- 跳序的真实后果：用户拿到的是"先大分镜4、后大分镜2"的候选，剪起来接不上，也看不出到底哪一块真的出片了。这个坑在真机上踩过。
- 顺序依据是**文件里的块序**（`storyboard action=episode-blocks` 返回的顺序），不是文件名排序、不是候选列表的时间倒序、也不是你记得的顺序。
- 每块出完先说一句"第 N 块已提交 / 已完成"，再动下一块；中途被打断就从最后一块**已完成**的往下接。

## 执行注意

- 视频很慢，`comfy_run` 的 `timeout_ms` 给足（默认 15 分钟，H3 建议 1800000 起）；超时不会丢任务，用 `comfy_job` 带 `prompt_id` 继续取。
- 显存：本条工作流很重。本机 RTX 3060 Laptop 6GB 低于 16GB 推荐线，视频默认推荐**云端 8888**，但不禁止本地。用户明确选本地时，先降低分辨率、Chunks 和步数，并准备处理爆显存。
- 参考图数量、`ref_image_size`（`match` / `max`）会影响速度：`max` 身份保真更好但**慢好几倍**。
- 产出命名：给 `364 VHS_VideoCombine` 的 `filename_prefix` 起个能认出来的名字（例如 `第1集-大分镜1`，
  **不要带"一采"字样**——这条工作流不抽卡，落盘的就是二采成片），方便把文件归到 `剧集/第N集/` 下。
  工作流默认是 `YZ_H3_`。
- **只有一个落盘节点 `#364`**：出片就是它，不存在"一采产物 / 二采产物"两份。
